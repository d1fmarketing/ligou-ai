# PLANO FINAL v4 — Ligou MVP: o funcionário que fala, vende, fecha e aprende

> **Arquitetura em uma linha:** Hermes decide, aprende e trabalha. Realtime conversa. O controller verifica poderes. O worker executa. O ledger prova. O dono concede ou revoga autoridade.

## Declaração-norte

> **Hermes vive, aprende e trabalha. A infraestrutura não decide por ele; apenas garante que os poderes que ele exerce foram concedidos, que a ação não duplica e que o resultado pode ser provado.**

## Contexto

RJ não é engenheiro — **Isa executa tudo sozinha**. MVP: pelo dashboard, ligar por voz (navegador) e falar com o agente em EN/ES como cliente novo; pedir agendamento; negociar e fechar serviço com preço acordado. Agente = funcionário + vendedor persistente que pesquisa, planeja, aprende e trabalha — com poderes concedidos, não travas. EC2 = casa. Telefone = última fase. Orçamento ~$350/mês. v3 = v2 (segurança técnica: ~75% preservado) + as 7 mudanças obrigatórias da revisão (Hermes como cérebro desde F1, autoridade graduada, estado Hermes real, vertical sintética agora, teardown de mercado, receipts com reconciliação, capabilities em vez de "zero credenciais").

## Arquitetura v3

```
OpenAI Realtime  = ouvido, voz, interrupção, reflexo rápido (gpt-realtime-2.1-mini; 2.1 comparado em F1)
Hermes na célula = CÉREBRO PERSISTENTE: planejamento, memória viva, skills, subagentes,
                   pesquisa, trabalho contínuo; participa seletivamente da ligação
Voice Controller = conecta Realtime ↔ Hermes ↔ capabilities (sideband autoritativo por chamada)
Supabase         = LEDGER AUTORITATIVO: identidade, poderes concedidos, políticas, casos,
                   outbox, compromissos externos, receipts, audit (não é o cérebro)
Action Worker    = mãos determinísticas (Google/CRM/SMS): outbox → mutação → reconciliação → receipt
```

Fluxo na chamada: `Realtime → tools determinísticas · consult_ligou_brain(topic enum + service_id validado) → contexto estruturado server-side → código de ação Hermes → orientação fixa do controller`. A antiga ponte de contexto/pergunta/prosa livre está aposentada e não pode ser reativada.

## Princípios (leis do plano)

1. **Anti confused-deputy (mantido do v2):** sessão de voz roda com capability própria (`actor=CALLER, tenant=server-derived, call=uuid, allowed_tools estreitas, exp+jti+audience`); dono loga só para conceder poderes e decidir casos; tools mutantes nunca no browser; modo degradado = responder, citar regras, `create_async_case` — nunca reservar/anunciar sucesso.
2. **Papéis:** Supabase = ledger autoritativo de identidade/poderes/políticas/compromissos/receipts/audit. **Hermes = cérebro operacional persistente do AgentSpace** — não fica atrás de "aprovação por ação": opera dentro de **autoridade graduada** (§3). Realtime = reflexos.
3. **Autoridade graduada — grants granulares, cores DERIVADAS (o dono concede PODERES, não aprova ações):** o registro real no ledger é
   `powers(subject, capability, resource, conditions, monetary_limit, geography, service_types, channel, allowed_hours, expires_at, version, granted_by, revoked_at, auth_epoch)`.
   Exemplo: *Hermes pode criar booking, para plumbing_diagnostic, em Orange County, seg–sáb 8h–18h, preço ≥ $149, até $750 estimado, enquanto policy_version=7.*
   VERDE/AZUL/AMARELO/VERMELHO/PRETO são a **linguagem de produto derivada** dos grants (VERDE=sozinho: pesquisa, working memory, lead scoring, notas, drafts, subagentes · AZUL=executa e registra: booking/estimate dentro do grant, SMS de confirmação, follow-up consentido · AMARELO=confirmação: fora de faixa, ambiguidade, emergência, refund, alto valor · VERMELHO=novo poder: sistema/credencial/campanha/política/pagamento/outbound em escala · PRETO=nunca: cross-tenant, segredos, apagar audit, desligar limites, auto-ampliar autoridade).
   **Revogar incrementa `auth_epoch` e invalida imediatamente os tokens de capability já emitidos.**
   Skills novas: ver §11 (esteira de autopromoção com avaliador independente).
4. **Estado Hermes é AgentSpace real, não cache — com precedência de memória definida:** Supabase guarda políticas, grants, casos, ações, bookings, receipts, audit e memória empresarial tipada; Hermes guarda working memory, procedimentos, skills, estratégias, histórico operacional e o modelo vivo da empresa. **Hermes aprende livremente na working memory — sem pedir aprovação por memória.** Camadas e precedência:
   `power/policy aprovada > memória empresarial aprovada > working memory > inferência da conversa atual`.
   Working memory alimenta raciocínio/estratégia/sugestões; só vira `approved_business_memory` (afeta atendimento) ou power (compromete a empresa) via aprovação. Isso evita split-brain sem amputar a aprendizagem.
   **Backup consistente com SQLite (não só snapshot com o processo vivo):** `hermes backup`/SQLite backup API → checksum → artefato criptografado por tenant → S3; snapshot EBS = disaster recovery. Restore testado em volume/host NOVO provando memória, skills, sessões e grants projetados — **sem restaurar credenciais antigas**.
5. **Capabilities, não chaveiro (reformulação do "zero credenciais"):** Hermes autentica o modelo somente por Codex OAuth da assinatura, em volume separado do estado cognitivo; a chave do API server é apenas local + **tokens de capability estreitos e temporários emitidos pelo controller**. Ele NÃO possui API key de modelo nem credenciais brutas de Google, Twilio, Supabase service-role, AWS ou de outros tenants.
6. **Receipts corrigidos:** `accepted` exige `external_id` **+ recurso confirmado por leitura/reconciliação + payload/hash compatível + tenant/mapping corretos + timestamp/provider request** — ID externo sozinho não prova nada. `failed` só com rejeição explícita. `unknown` = reconciliar antes de qualquer retry. Fluxo: `action_intent → idempotency_record (chave server-issued ligada a tenant+versão+preço+slot+mapping+snapshot de policy) → outbox transacional → worker com lease → mutação → read-back → receipt`.
7. **RPCs endurecidas (mantido):** `SECURITY DEFINER` com `search_path=''`, revoke de PUBLIC/anon, tenant/actor de contexto verificado, lock de versão/hash, pgTAP adversarial. RLS `FORCE`; nenhuma service-role no browser nem na célula.
8. **Ciclo OpenAI correto (mantido):** cache texto $0.06/M best-effort (medir `cached_tokens`); `ek_` só conecta (60min = nova sessão com contexto transferido; MVP cap 15min); function tools ≠ MCP (adaptadores separados); budget = reserva atômica de cota + sideband derruba sessão no teto.
9. **Aprovação assíncrona no piloto (mantido):** fora de poder → `ASYNC_CASE` → "the team will confirm" → nunca segura o cliente; dono decide depois; ajuste de termos → cliente reconfirma. Same-call approval = escalação futura.
10. **Containers = contenção (mantido):** checklist de hardening antes do tenant 2; tunnel nomeado com spike de SSE; 1 EC2 t3.large no MVP.
11. **Autopromoção de skills com avaliador independente (Hermes não emite o próprio certificado):**
    `Hermes cria skill → capability manifest automático → scanner independente → testes mantidos pela Ligou → sandbox sem credenciais → canário só naquele tenant → digest imutável → promoção → rollback automático`.
    Usa só poderes existentes e passa a esteira = promove sozinha, sem clique humano. Pede poder novo = vai ao dono (VERMELHO).
12. **Follow-up automático exige grant de comunicação completo:** consentimento e origem, canal, destinatário, finalidade, template/limites de conteúdo, quiet hours, frequência, opt-out, duração da autorização. Com o grant, cada mensagem sai sozinha e registrada — sem ir ao dono.
13. **Pin do Hermes de verdade:** release **`v2026.8.18`** (nome comercial: v0.20.4) + commit SHA verificado + **digest imutável da imagem Docker** + hash da config. Nada de tag mutável.
14. **"Mesma config" browser/telefone = builder canônico + dois adapters** (WebRTC e SIP), não payload literalmente igual. `consult_ligou_brain` aceita apenas tópico enumerado + serviço validado; o server exclui PII/transcript/endereço/piso e Hermes retorna somente um código de ação em schema fechado, mapeado a texto fixo. Nenhuma prosa do modelo volta direto à chamada.

## Empresa sintética (decidida agora, trocável)

**Plumbing ("Rocha Plumbing", sintética)** — escolhida por exercitar TODO o espectro de poderes: urgência/emergência (AMARELO), estimates dentro de faixa (AZUL), agendamento, negociação de preço, exceções, follow-up. Cleaning e HVAC ficam como fixtures secundários de eval. O primeiro tenant REAL continua sendo escolhido por RJ na F5.

## Tools da chamada

Leitura (controller/cache, <300ms): `get_business_info · quote_price` (sem regra → `needs_owner`) `· check_availability` (slots COM preço). Mutantes-AZUL: `propose_booking · close_deal` (piso server-side → intent → outbox → `accepted` a tempo = "booked"; senão "confirmation shortly"). AMARELO/fora: `create_async_case`. Profundo: **`consult_ligou_brain`** com tópico enumerado e serviço validado; timeout curto, resposta JSON fechada e orientação fixa — nunca contexto/pergunta livre nem advice do modelo.

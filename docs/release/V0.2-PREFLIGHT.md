## Blocking Hermes evidence

The legacy container stores `auth.json` inside its combined `/opt/data` volume.
The RC Compose claims a separate model-auth volume at `/root/.hermes`, but the
pinned Hermes image sets `HERMES_HOME=/opt/data`. Runtime inspection of the
image confirmed that openai-codex login and refresh always read and write
`get_hermes_home()/auth.json`; Codex CLI credentials are imported into that same
store rather than used in place.

A profile-based nested-volume layout was tested. It could read global auth, but
refresh/login would write a new auth store into the cognitive profile. An
independent review classified this Important. The change was reverted, the new
unauthenticated tenant container was stopped, and its volumes were retained.
The healthy legacy container was restarted. No cognitive or auth volume was
deleted.

Therefore the fixed Hermes digest cannot currently satisfy both:

1. persistent openai-codex login/refresh; and
2. a cognitive volume that never contains reusable authentication.

Deploying the RC would make the backup/auth claim false and is prohibited.

## Verdict and unblock

`V0_2_BROWSER_PILOT_NOT_READY`

Smallest external unblock: publish and approve a Linux/amd64 Hermes image whose
auth implementation supports an independent writable auth root (for example
`HERMES_AUTH_HOME=/root/.hermes`) for login, pool synchronization, and token
refresh while `HERMES_HOME` remains the cognitive root. The new image must be
pinned by repository digest, exercised against real login plus forced refresh,
and prove that cognitive backup contains no auth material before EC2 deployment
or browser-pilot implementation resumes.

### Budget leak found by the proof and fixed

Because media never connected, `provider_usage_state` stayed `unknown`, and
`settle_call_budget` refuses to settle in that state — by design, to never
guess a cost. But nothing bounded the retry: the reservation held its full
$1.50 ceiling forever. Production already had **five** such reservations
holding **$6.00 of the tenant's $15.00 daily budget**, the oldest from
2026-08-19; real calls would soon have been denied.

Migration `20260822053000_bounded_unresolved_budget_settlement.sql` (additive,
functions only) adds the bounded terminal path, and commit `5cd1830` wires the
reconciliation worker to it. Once a call is durably terminal AND the provider
is confirmed done AND the bounded attempt count is reached, the reservation
settles at the rate it was priced at (ceiling ÷ session length) for the
duration the call durably recorded, capped by the reservation. It is
deliberately not a release to zero: an unresolvable call is charged an honest
estimate rather than forgiven. Every guard is enforced inside the SQL function.

Verified live: remote history 48/48 aligned with zero pending, release
`5cd1830` activated with all three checks ready, and the stuck reservations
began draining immediately (5 → 3 active, $6.00 → $3.00 held) with the
remainder converging as their attempt counts reach the bound.

Trade-off worth revisiting: the estimate rate is the reservation rate, which is
a ceiling rate, so unresolvable calls are charged slightly high. Charging low
would understate spend against the daily cap, so the safe direction was chosen.

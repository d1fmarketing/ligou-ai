# V0.2 — Response ownership after the onboarding lifecycle refactor

Implementation baseline: `c49acd4` plus Task 5 working changes (2026-08-25).
This is a code/test inventory, not production-deployment evidence.

## One authority, one adapter

For an onboarding call, `onboarding-coordinator.ts` is the only authority that
decides whether the application may:

1. ask the greeting or next coverage question;
2. prepare and speak the digest-bound summary;
3. accept a fresh explicit owner acknowledgement;
4. speak the approval-bound final signoff;
5. request provider termination.

`sideband.ts` owns no independent onboarding phase, recap counter, refusal
counter, summary watchdog or close-grace timer. It keeps one reducer state per
`SessionLedger`, preserves it across socket reattachment, serializes raw events,
executes reducer commands and persists the existing terminal/budget ledger.

## Producers that can create speech

| Producer | Trigger | Identity / gate |
|---|---|---|
| OpenAI semantic VAD | completed caller turn | provider-managed automatic response; no application intent correlation |
| reducer `request_response` | greeting | `greeting:<call-id>` |
| reducer `request_response` | acknowledged closed tool batch | `tool-batch:<provider-response-id>:<ordered-batch-hash>` |
| reducer `request_response` | complete authoritative snapshot | `summary:<snapshot-digest>` |
| reducer `request_response` | persisted immutable voice acknowledgement | `final-signoff:<approval-receipt-id>` |

All four application-created cases pass through `requestResponse`. The adapter
correlates the provider response only when
`response.created.response.metadata.intent_key` contains the exact key. A
metadata-less VAD response can be active and terminal, but can never claim a
summary/signoff/application intent by FIFO guess.

`request_signoff` is informational. The paired keyed `request_response` is the
single frame sender, so signoff cannot be requested twice.

## Raw Realtime event mapping

| Provider event | Reducer evidence | Exact identity |
|---|---|---|
| `response.created` | `response.created` | `response.id`; optional metadata `intent_key` |
| `response.output_item.done` function item | buffered until parent terminal | `response_id` + `item.call_id` |
| `response.output_audio_transcript.delta/done` | summary transcript proof | `response_id` |
| `response.output_audio.done` | summary/signoff audio-generation proof | `response_id` |
| `response.done` | closed ordered tool batch + response terminal | `response.id` |
| `output_audio_buffer.stopped` | playback-complete proof | `response_id`; missing identity is rejected |
| `conversation.item.created` output echo | tool output acknowledgement | deterministic `item.id` |
| caller `speech_started` | fresh owner turn + audio interruption | exact `item_id` or controller turn ID |
| `response.cancelled` / `output_audio_buffer.cleared` | audio interruption | exact `response_id` |
| `session.ended` before finalization | interrupted/error outcome | never successful onboarding |

Every onboarding raw event enters one per-call promise queue. Store calls,
socket sends, reducer events and follow-on commands therefore cannot overtake
one another, even though WebSocket callbacks arrive fire-and-forget.

Only `item.status=completed` function items inside a
`response.done.response.status=completed` parent are executable. Cancelled,
failed, incomplete or status-less items/responses block with zero tool, store or
output effects.

One exception is transport-only cancellation: a `cancelled` response with zero
buffered function items is ordinary barge-in bookkeeping. Its exact audio proof
is interrupted and its response becomes terminal without blocking the call. If
it represented the current speech turn, that turn stays pending and the next
metadata-less VAD response rebinds it; only a later `completed` terminal may
drain one still-current application intent. Cancelled responses containing any
function item remain fail-closed.

## Complete tool batches and reconnect-safe output

Function items are grouped under their exact parent provider response. Each
requires one nonnegative integer provider `output_index`; duplicate or invalid
indexes block. The adapter waits for terminal `response.done`, sorts function
membership by numeric `output_index` (gaps are legal because non-function output
can occupy intervening slots), then computes SHA-256 over complete ordered
membership `(output_index, call_id, tool name, canonical args hash)`. The reducer
receives every `tool.called`, then one `tool.batch_closed` with that stable hash.

Before the first member executes, the complete sorted batch is preflighted
against every reducer receipt/call identity and the bounded replay registries.
A changed cross-response `call_id`, capacity violation or already blocked
lifecycle rejects the whole batch; no sibling tool can run after the failure.

The durable state sequence is:

```text
running -> executed -> output_pending -> output_acked
```

- `record_interview_answer` receives the exact provider `item.call_id`.
- Execution/persistence finishes before transport delivery.
- The output frame uses `item.id = tool-output:<call-id>`.
- A successful socket send produces `tool.output_sent`.
- Only an echoed `conversation.item.created` with that exact ID produces
  `tool.output_acked`.
- Reattach resends `executed`/`output_pending` with the same ID and never reruns
  persistence.
- A reducer-issued application response command whose socket send threw remains
  `queued` in the adapter and is retried on the next generation. Once a send
  succeeds it becomes `sent` and is never guessed/replayed merely because its
  acknowledgement or terminal event is missing.
- Continuation is eligible once, only after every declared batch output is
  acknowledged and the exact parent response is terminal.
- A semantic store result marked `reused` at or behind the current lifecycle
  revision is delivered/acknowledged as an idempotent result but never emits a
  regressive `coverage.changed`. A real newer revision still advances coverage.

## Summary, approval and refresh ownership

`prepare_summary` calls `loadOnboardingSnapshot` and returns the discriminated
result through `snapshot.loaded`. Snapshot timeout, query error, empty,
incomplete, changed identity, partial rules or empty factual anchors block; none
degrade to an ungrounded response.

If approval persistence reports `changed`, the reducer:

1. emits a deterministic `snapshot_changed` output for the approval tool;
2. issues one correlated `refresh_snapshot` request;
3. accepts only a strictly newer complete authoritative result under the exact
   request ID;
4. waits for approval-tool output acknowledgement and the terminal parent batch;
5. then issues a distinct ordinary `prepare_summary` load for the new digest.

Voice acknowledgement remains evidence only. It approves no rule, grants no
power and changes no operational mode.

Speech ingress increments a call-local generation synchronously before the raw
event waits on the queue. Snapshot/store completion from an older generation
may prepare a still-valid keyed intent, but cannot send it over current owner
speech. A metadata-less same-socket VAD response consumes that turn; when its
completed terminal arrives, queued valid application intents are retried.

Coverage advancement terminalizes every queued/sent summary intent for an old
digest. Pending adapter commands are pruned by purpose-specific identity:
summary digest must equal both current coverage and summary; signoff receipt
must equal current approval and signoff. Late provider acknowledgement for an
invalidated old summary is ignored without rebinding it.

The same correction invalidates every nonterminal `final_signoff` intent bound
to the prior approval, clears its active-response correlation and drops its
pending adapter command. Late response evidence for the old approval is ignored;
a corrected digest must complete a new spoken summary and immutable approval
before a new signoff key can exist.

## End-session and termination ownership

Every onboarding `end_session` tool item, including the first through the
hundredth premature attempt, receives:

```json
{"status":"application_owned_close","ending":false}
```

There is no refusal-count bypass and no timer/grace path. The only ordinary
onboarding close path is:

```text
valid summary playback
-> fresh explicit owner assent
-> immutable approval receipt + output acknowledgement
-> final signoff audio generated
-> final response terminal
-> exact output playback stopped
-> reducer request_hangup
-> existing at-most-once provider termination
-> exact terminal call readback + provider_termination_state=confirmed
-> reducer closed
```

Budget settlement may remain deferred when provider usage is unresolved. That
does not authorize another provider request and does not erase already durable
provider + terminal-call proof.

After the hangup key is consumed and phase is `provider_terminating`, repeated
late transcript/audio/response/playback evidence for the same signoff is an
exact state no-op. It cannot add usage twice or request another hangup; the exact
durable confirmation event can still move the reducer to `closed`.

Per-call response buffers are capped at 512 and deterministically prune the
oldest terminal transport projection. Reducer tool receipts, tool batches and
response intents, plus pending adapter response commands, are capped at 512 and
fail closed without deleting replay identities when saturated. One provider
response may contain at most 100 function items.

The reducer terminal-response identity list is also capped at 512. It prunes
only identities not referenced by a live tool batch, active response,
summary/signoff or nonterminal response intent. If every identity is still a
replay dependency, the next terminal event blocks safely instead of discarding
authority evidence.

`blocked` is absorbing for authority but not for safe evidence. On attach it
advances only the socket generation, terminalizes/prunes all pending authority
speech and resends exact executed/output-pending function results. Durable tool
completion, output send/ack and response terminal remain bookkeeping-only and
never call coverage advancement. An exact already-requested hangup confirmation
with terminal persistence may still close the lifecycle; mismatched or
unrequested confirmation remains blocked.

Deadline, phone heartbeat, socket backoff/retry, cost kill switch, durable
provider reconciliation and budget reconciliation remain in place.

## Non-onboarding boundary

Customer and owner-browser sessions retain their legacy response-continuation,
usage, phone activation/heartbeat, retry and terminal-settlement behavior. They
do not receive onboarding lifecycle state, onboarding tools or onboarding close
authority.

# V0.2 — Response-ownership inventory (voice orchestration)

Snapshot at `c7c03f3` (2026-08-25), before the single-coordinator refactor.
Method: exhaustive grep for every speech-lifecycle term across
`voice-controller/src`, `dashboard/src/voice`, `supabase/functions`, plus a
line-by-line read of `sideband.ts` (the file carries 11 independent review
rounds from the M2 defect chain).

## Producers that can CREATE speech

| # | Site | Trigger | Key / guard | Verdict |
|---|------|---------|-------------|---------|
| 1 | `sideband.ts` `activateOpenedSocket` (greeting) | first socket attach of a browser call | `ledger.greetingRequested` (once per call, survives reattach); `!options.phone` | moves into coordinator |
| 2 | `sideband.ts` `maybeContinueResponse` | `response.done` after tool outputs delivered | `continuationWanted` batch flag, consumed once; `responseActive` + `pendingToolCalls` gates | moves into coordinator |
| 3 | `sideband.ts` recap-push timer | `response.done` while a recap is owed and the turn idles | `recapPushes` (bound 3, counts schedules), `speech_started` cancels, fire-time re-guard | moves into coordinator |
| 4 | OpenAI server VAD | end of user speech | provider-internal | stays: configured explicitly (semantic_vad, low) instead of implicit default |

No other file can create a response. The browser (`session.js`,
`VoicePanel.jsx`) sends **zero** conversation events — the data channel is
read-only captions; React effects only tear down local media.

## Producers that can CANCEL / INTERRUPT speech

Application level: **none**. Barge-in is exclusively the provider's native
WebRTC interruption/truncation. There is no `response.cancel`,
`session.interrupt`, `output_audio_buffer.clear` or
`conversation.item.truncate` anywhere in the repo. Manual "stop" is the
owner's hangup button (local teardown + normal terminal flow).

## Producers that can END the session

| Site | Trigger | Guard |
|------|---------|-------|
| `end_session` tool → agent-end grace → finalize | model, after recap gate passes | recap gate (substantive later-response speech), 2-refusal bounded honor, audited provider hangup |
| deadline timer | `expiresAt` | terminal, bounded |
| budget kill-switch | cost cap per turn | terminal, bounded |
| caller hangup / `session.ended` | provider | native |
| reaper / reconciliation workers | durably stale calls | at-most-once DB machinery |
| browser `end()` | user button, deadline, remote-hangup detection | local teardown only — never sends conversation events |

## Answers to the eight inventory questions

1. **`response.create` senders:** 3 application sites, all in `sideband.ts`,
   plus the provider's automatic user-turn response. Nothing in React, edge
   functions, or timers outside those three.
2. **Cancel/interrupt senders:** 0 application-level; native barge-in only.
3. **Greeting triggers:** 1, keyed (`greetingRequested`), never on reattach,
   never on phone. The prompt shapes the wording; the lifecycle owns the
   trigger.
4. **Onboarding advancement:** the model steers topics (deliberate); the
   orchestrator owns only the enforced invariants (recap owed → refuse close,
   idle turn while recap owed → bounded push).
5. **Hangup requesters:** 1 audited path (`agent_ended_session` through the
   at-most-once provider-termination machinery) plus the bounded lifecycle
   killers above.
6. **Automatic + manual mixing:** yes, by design — manual creates are gated by
   `responseActive` and the `conversation_already_has_active_response` error
   is recoverable (flags re-arm, next `response.done` retries). The session
   previously ran the *implicit default* server VAD; it now becomes an
   explicit `semantic_vad`/`eagerness: low` with `create_response` +
   `interrupt_response`, declared at session creation AND re-asserted in the
   sideband's `session.update` (update semantics for nested objects are not
   merge-guaranteed, so both sites carry the same config).
7. **Duplicate continuation for one function call:** the continuation is
   batch-keyed and exactly-once, BUT a duplicated `response.output_item.done`
   for the same `call_id` would re-execute the tool (double insert). **Real
   gap** → fixed by per-call-id dedup in the coordinator.
8. **Stale socket replay:** fenced by `ownsSocket`/`canHandleMessage` +
   reattach flag resets; verified across the M2 review chain, retested.

## Deltas implemented in this run

- Explicit `semantic_vad` (eagerness low, create_response, interrupt_response)
  at session creation and in the sideband `session.update`.
- `ResponseCoordinator` (`voice-controller/src/response-coordinator.ts`): the
  only application authority for greeting / continuation / recap push / close
  eligibility, with idempotency keys, single-active-response accounting and
  the per-call-id tool dedup.
- Deterministic summary grounding: when the coordinator forces the owed recap
  (push or `end_session` refusal), the refusal/output carries the persisted
  snapshot of this call's registered rules, so the spoken summary reads from
  the database, not from the model's memory of the transcript.
- Structured lifecycle telemetry (`voice_evt` lines with call id, response
  id, state, elapsed) replacing ad-hoc log strings.
- No new prompt rules; the narration rule stays as a single instruction.
